1整体架构与技术选型

👨‍🏫 老师

入口 main.py 导入了一个叫 local_shims 的模块。它到底是什么？为什么一个"本地运行"的项目要专门写一个兼容层？说清楚它的动机和边界。

🎓 学生

local_shims 是平台解耦层。项目最初在 Coze/扣子托管平台开发，原始代码大量依赖 coze_coding_utils / coze_coding_dev_sdk 提供 Context、日志、错误分类、流式 Runner、Agent 加载、异步任务运行时。为脱离平台在本地零依赖运行，我做了这些接口的最小可运行等价实现。

共 11 块：Context 用 dataclass+uuid 复刻；request_context 用 contextvars.ContextVar 保证协程安全；setup_logging 用 RotatingFileHandler；graph_helper 用 importlib 动态加载 agent。核心原则是保持签名完全一致，业务代码一行不改，只换 import 来源。

👨‍🏫 老师

你 shim 里 AsyncTaskRuntime.submit 就是直接 await graph.ainvoke，get 永远返回 None。你把平台的异步任务持久化阉割成了同步阻塞，那 /run 的超时控制、任务取消还有意义吗？

🎓 学生

有意义，但层次不同。AsyncTaskRuntime 是降级桩。真正的生命周期管理没依赖它，而是在 GraphService 里用原生 asyncio 重写：asyncio.create_task 登记进 running_tasks 字典，asyncio.wait_for(task, timeout=900) 做超时，超时后 task.cancel()，并 except asyncio.CancelledError 优雅处理。那个 shim 在当前调用链其实是死代码，保留只为 import 不报错、未来平滑接回平台。

👨‍🏫 老师

为什么选 LangGraph 的 create_react_agent，而不是自写状态机？你业务流程是强顺序的——先校验、再算指标、再检索、最后导出。顺序固定，ReAct 让 LLM 自主决策不是画蛇添足？

🎓 学生

业务流程看似固定实则动态：① 工具调用数量参数不确定——search_regulations 要对每条风险各检索一次，风险几条只有 LLM 读完年报才知道；② 存在条件分支——单公司/批量 batch_analyze_companies/多年 compare_multi_year、图表三选一；③ ReAct 自主性我用两道护栏兜住：系统提示词"强制规则"约束顺序 + 代码层 _AgentWrapper 兜底。所以是"LLM 决策 + 硬编码兜底"混合架构，不是纯放养。

2Agent 核心——滑动窗口的致命隐患

👨‍🏫 老师

agent.py 的 _windowed_messages 写的是 add_messages(old,new)[-40:]，挂在 AgentState.messages 的 reducer 上。这个无脑切片会切出什么后果？

🎓 学生

本项目最危险的一处。OpenAI 协议要求每个 AIMessage 的 tool_calls 后必须紧跟 tool_call_id 匹配的 ToolMessage。[-40:] 从尾部粗暴截取，极可能保留 AIMessage(带 tool_calls) 却挤掉对应 ToolMessage，或留下孤儿 ToolMessage。两种情况 DeepSeek/OpenAI 都会返回 400。

👨‍🏫 老师

既然明知道，为什么不修？

🎓 学生

做了风险评估，判断当前用量可控但承认是待办缺陷。单次审计工具调用约 10~13 次，消息总数 30~40 条边缘，40 是贴着单轮满链路上限设的。真正风险在多轮对话——同一 thread_id 追问累积超 40，截断会切开中间某个 tool 配对。正解：把 reducer 换成按对话轮次原子块裁剪，或用 trim_messages(start_on="human")。

👨‍🏫 老师

_post_process 用 ToolMessage 集合判断 PDF/Excel 有没导出。如果滑动窗口刚好把 export_pdf_report 的 ToolMessage 截掉，你会误判"没导出"重复导出。你这兜底会不会打自己？

🎓 学生

会。这是两机制的耦合缺陷。result.get("messages") 经过同一个被 window 过的 state，若导出发生很早又被挤出 40 条，called 集合不含 export_pdf_report，兜底会重复生成一份 PDF——不崩，但脏输出。根治还是修 reducer，两个 bug 是同一根因。

3流式与同步的一致性缺陷

👨‍🏫 老师

_AgentWrapper 只重写了 invoke/ainvoke 调 _post_process。但 /stream_run 走 agent.astream，而你根本没定义 astream。它怎么被调用到的？这条路径上辩论和兜底还执行吗？

🎓 学生

本项目同步/流式行为不一致的核心问题。_AgentWrapper 的 __getattr__ 会透传未定义属性给底层 agent，所以 astream 完全绕过了 _AgentWrapper。结果：/run(ainvoke) 会执行兜底导出+三方辩论+综合评分；/stream_run(astream) 一次都不跑。

👨‍🏫 老师

前端主用哪条？这不是严重的功能不对等吗——流式用户拿到的报告没辩论复核、没兜底导出？

🎓 学生

前端主用 /stream_run，所以实际生效路径缺失了增强功能，我不辩护。部分补偿：① 导出不完全靠兜底——提示词强制 LLM 主动调用导出，_build_final_report_from_messages 也用正则抓 /local_storage/*.pdf|xlsx 链接；② 辩论复核确实丢失，是真实缺陷。正解：给 _AgentWrapper 补一个 astream 包装，透传 chunk 做进度，末尾用积累消息跑一次 _post_process 再作为最后 SSE 事件推出。

👨‍🏫 老师

stream_sse 里 AI 每吐一段就 current_pct+1 加到 96。这进度条是真实还是演戏？

🎓 学生

一半真一半"演"。真实：工具阶段命中 TOOL_NAME_TO_STEP 就跳到预设百分比（解析 8%/算指标 18%/导出PDF 85%），这些是真实执行锚点。启发式：锚点之间用"每段+1%封顶96%"制造平滑观感，避免卡死让用户以为死机。属于不可精确度量任务的进度估计，填充部分与真实工作量无严格对应。

4RAG 知识库——分块、缓存失效与依赖地雷

👨‍🏫 老师

local_knowledge.py 用正则 (?=第[一二三四...]+条) 分块，len(splits)>3 才用。为什么用前瞻断言而不是普通 split？>3 这个魔数依据是什么？

🎓 学生

前瞻 (?=...) 是零宽匹配，只在"第X条"前切一刀、不消费字符，所以每块开头完整保留条款号——这是最强语义锚点和引用凭据，报告 regulatory_basis 要写"依据第N条"。>3 是文本类型判别启发式：能切 3 段以上判定为法规条文按条款细分，切不出来的（cases_*.txt 案例）按自然段分。3 是经验值，严谨应按"条款数/总长度"密度判别。

👨‍🏫 老师

缓存判断 if collection.count() != len(chunks): 重建。用户改了某法规内容但条款数没变，你这缓存会怎样？

🎓 学生

会命中脏缓存返回旧内容。count 只感知块数量、感知不到内容变化，新内容永远进不了索引。规避靠 /api/reload_kb 或 /api/upload_kb 强制重扫，但原地改文件不会自动失效。根治：给每块 metadata 加内容 md5 哈希，或对整个目录算指纹，指纹变了才重建。

👨‍🏫 老师

最狠一刀：Dockerfile 第 31 行预下载 sentence_transformers 模型，但 pyproject.toml 根本没有这个依赖。你这镜像能 build 出来吗？

🎓 学生

当前依赖下会 build 失败（ModuleNotFoundError），是真实构建断裂。成因：chromadb 默认嵌入用 ONNX 版 all-MiniLM-L6-v2，并不硬性依赖 sentence-transformers；我写这行意图是"烤进镜像避免联网超时"但误用了包名。影响分环境：本地运行不走 Dockerfile、chromadb 自己按需下 ONNX，所以本地一直好的；Docker 路径坏的。正解：改用 chromadb 自带 DefaultEmbeddingFunction() 预热，或显式加依赖。根因是两条部署路径没有同等测试覆盖。

5工具实现的边界 bug 与算法缺陷

👨‍🏫 老师

financial_calculator.py 存货周转 avg_inv=(inv_c+(inv_p or inv_c))/2。inv_p or inv_c 想干嘛？这藏了个 bug，自己找出来。

🎓 学生

Python 真值陷阱。本意是"没提供 inv_p（None）就退化用本期"。但 or 判的是假值不是 None——若上期存货合法等于 0（新公司/纯服务业），0 or inv_c 返回 inv_c，把真实为 0 的期初错误替换，周转率失真。正解：inv_p if inv_p is not None else inv_c。凡用 x or default 处理数值型财务数据、且 0 合法的地方都有此隐患，数值计算必须用 is None 而非真值判断。

👨‍🏫 老师

_pct_change 用 (current-previous)/abs(previous)。为什么分母取绝对值？什么情况会给出违反直觉的结果？

🎓 学生

取 abs 是为保留变动方向符号——不取的话上期为负时正负号抵消导致方向错乱。但上期为负、本期跨零时仍违反直觉：上期 -100、本期 +50，给出 +150% 读起来像"增长"，实际是扭亏为盈（没有良定义增长率）。这种应特殊标注为'扭亏/减亏'定性描述而非给数字，当前实现输出的是数学正确但语义误导的百分数。

👨‍🏫 老师

_extract_risk_json 用大括号深度计数抠 JSON。什么情况会抠错？

🎓 学生

没处理字符串字面量内部的括号。depth 无差别遇 { 加一、遇 } 减一，不知自己是否在字符串内。若风险描述含大括号如 "evidence":"货币资金{注:含受限}..."，depth 提前失衡，抠出语法残缺子串。有兜底：json.loads 校验+检查必含字段，失败返回 None——不崩但会静默丢失结构化报告退化为纯文本。正解：用支持字符串状态机的解析器，或约束 LLM 用 ```json 代码块包裹。

6数据库设计与会话状态

👨‍🏫 老师

main.py import 了 get_session/get_engine/Base，但整个文件一次都没调用。db.py 写了 166 行连接池、重试、双模式，业务流程根本不碰数据库。你这是堆砌代码充门面吗？

🎓 学生

如实说：当前业务数据确实不落库——报告图表存文件，会话用内存 checkpointer，db.py 在当前调用链没有实际读写。这是从平台版继承的基础设施骨架。保留理由：① 设计本身可直接启用——三级 URL 优先级、连接重试（应对 Docker 慢启动）、SQLite 单连接/PG 连接池，一旦要落库 get_session() 就能用；② .env.example 留了 PGDATABASE_URL 开关。但您批评成立：当前就是未接线预留件，属 YAGNI 反例。

👨‍🏫 老师

MemorySaver 纯内存，thread_id 绑 ctx.run_id。两个后果：多轮对话能续上吗？长期跑会内存泄漏吗？

🎓 学生

① 会话续接依赖客户端配合：thread_id=run_id，而 run_id 优先取请求头 x-run-id、没有才新 uuid。要多轮记忆客户端必须带同一 x-run-id，否则是无状态单轮。② 确实会内存泄漏：MemorySaver 永不淘汰，每个不同 thread_id 沉淀一份状态，重启才释放。正解：换 SqliteSaver / PostgresSaver 落到 db.py 那套连接——既解决泄漏又解决重启丢失。上一题"db.py 悬空"和这题"内存泄漏"恰好互为解药，一次重构一起消掉，这是架构上最该优先做的事。

7安全审查

👨‍🏫 老师

CORS 同时写 allow_origins=["*"] 和 allow_credentials=True。这个组合在浏览器里意味着什么？

🎓 学生

自相矛盾且不安全。按 CORS 规范，Allow-Credentials: true 时 Allow-Origin 不允许通配符，浏览器会直接拒绝。语义上等于"信任任何来源并允许携带凭证"，最宽松危险配置。正解：纯公开只读就 allow_credentials=False 配 *；要凭证就配显式白名单。本项目本地工具不需要 credentials，最干净是关掉它。

👨‍🏫 老师

所有接口一个鉴权都没有。任何人访问到端口就能烧你 API Key、塞文件。怎么解释？

🎓 学生

信任边界问题。当前定位本地单机、面向"审计人员自己电脑跑"，无鉴权可接受。但不回避风险：绑的是 0.0.0.0 而非 127.0.0.1，同网段任何人都能访问，一旦上公网就是烧 Key/污染知识库/耗磁盘。加固：① 默认绑回 127.0.0.1；② 加 X-API-Key 中间件对写操作强制校验；③ Key 已通过 .env 环境变量注入而非硬编码，这点是对的。

👨‍🏫 老师

/upload 用 uuid_+f.filename 拼路径，filename 用户可控。想想路径穿越。

🎓 学生

有路径穿越残余风险。若构造 ../../../Windows/Temp/evil.txt，uuid 只在第一段，后面的 ../ 依然生效跳出目录。正解：落盘前 os.path.basename() 剥路径成分。对比之下 /api/upload_kb 做对了——用 re.sub 把分隔符全替换成下划线。是两个上传接口安全强度不一致，把 /upload 也套上同样净化即可。

👨‍🏫 老师

/upload 用 await f.read() 一次性读进内存，上限 100MB。并发几个大文件会怎样？

🎓 学生

会内存尖峰。全量读入 + 解析时 PdfReader/pandas 再复制一份，单文件峰值两三百 MB，并发叠加可能 OOM。且 f.size 预检可能为 None，len(content) 二次检查时已读进内存、拦截太晚。正解：流式落盘+边读边计数，分块写入超限即中断删文件，内存只占一个 chunk。

8部署与运行环境

👨‍🏫 老师

为什么专门配 reload_includes=["*.py"] 和一长串 reload_excludes？workers=1 在生产是不是瓶颈？

🎓 学生

① reload 白名单防热重载死循环：服务运行时持续写 app.log/.chroma_db/local_storage/.db，不排除就"写日志→reload→重启中又写→再 reload"形成重启风暴。所以只监控 *.py，排除这些写入目录；HTML/CSS/JS 每次请求实时 read_text，改了立即生效无需 reload。

② workers=1 合理：reload 与多 worker 本身互斥；更关键——会话用进程内 MemorySaver，多 worker 进程内存不共享，同 thread_id 被分到不同 worker 就读不到彼此 checkpoint、多轮记忆失效。想上多 worker 前提是先把 checkpointer 换成数据库持久化——又指向同一重构。

👨‍🏫 老师

Dockerfile 先 COPY pyproject.toml uv.lock 再 uv sync，然后才 COPY 源码。这顺序是随手写还是有意？

🎓 学生

有意的，利用 Docker 层缓存。依赖变化频率远低于源码。若先 COPY 源码，改一行代码就导致后面 uv sync 层失效、每次重装全部依赖。反过来：依赖没动 uv sync 层永远命中缓存，改代码只重建最后几层。--frozen 按 lock 锁定版本保证可复现，--no-dev 跳过 pytest 减小体积。不过第 31 行那个 sentence_transformers 预热是败笔，得先修那行镜像才真正可用。

✦答辩总结陈词

🎓 学生 · 自评

扎实的部分：① local_shims 平台解耦证明可移植性；② "LLM 决策+硬编码兜底"混合 Agent 务实；③ RAG 法规按条款前瞻分块 + ChromaDB 向量检索带 TF-IDF 降级；④ 16 项指标 + 三大勾稽校验 + 五维风险，领域逻辑扎实；⑤ Dockerfile 分层、db.py 连接重试等工程细节到位。

清楚的窟窿（按优先级）：P0 致命——滑动窗口切断 tool 配对触发 400 + 兜底误判重复导出；astream 经 __getattr__ 绕过 _post_process 丢失辩论复核。P1 架构债——MemorySaver 内存泄漏+重启丢状态+锁死单 worker，db.py 悬空未接，应合并为"checkpointer 落库"一次重构。P2 质量——ChromaDB 缓存靠块数判失效、inv 0 值真值陷阱、JSON 括号提取、pct_change 负基数误导。P3 安全/部署——CORS 矛盾、无鉴权+绑 0.0.0.0、路径穿越、全量读内存、Dockerfile 依赖缺失。

态度：这些不是不知道才留着，是赛期约束下的取舍，每个都能说清根因和修法。工程能力不在零缺陷，而在清楚知道边界、雷在哪、按什么顺序拆。
