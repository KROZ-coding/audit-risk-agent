## 一、项目背景与拟解决的问题

### 1.1 行业背景

上市公司年度报告是投资者、监管机构与审计师获取公司经营与财务状况的核心公开信息载体。
一份 A 股主板年报通常有 200~500 页，包含财务报表、附注、公司治理、董事会报告、关联交易、
担保、诉讼仲裁、股权质押等大量信息，且这些信息分散在不同章节、彼此需要交叉验证。

与此同时，注册制全面实施后，上市公司数量与信息披露密度持续上升，而具备完整审计判断能力的
专业人员增长有限。会计师事务所的审计资源被大量消耗在"翻报表、找异常"等重复性劳动上，
真正需要职业判断的环节反而时间不足。

### 1.2 三大痛点（拟解决的问题）

| # | 痛点 | 具体表现 | 后果 |
|---|---|---|---|
| 1 | **量大** | 单份年报数百页，人工逐页阅读耗时数小时；批量审阅时数量级放大 | 审计效率低，覆盖不完整 |
| 2 | **点散** | 风险线索散落在报表、附注、管理层讨论、治理章节等多处，需交叉比对才能形成判断 | 单点阅读容易漏掉跨章节的传导线索 |
| 3 | **靠经验** | 能否发现异常高度依赖审计师个人经验与精力状态 | 新手易漏判；资深人力紧张；判断标准不统一 |

### 1.3 真实案例背景

近年来的重大财务造假与风险事件，事后复盘都能在年报中找到明显的报表异常或披露异常信号，
说明"信息本身是公开的、信号是存在的"，难点在于**在海量文本中及时、系统地把信号识别出来**：

| 案例 | 年份 | 事后可见的关键信号 | 本项目对应维度 |
|---|---|---|---|
| 康得新 | 2018 | 存贷双高（账面高额货币资金同时高额有息负债） | 财务风险 |
| 康美药业 | 2018 | 关联方资金占用、货币资金与经营现金流严重背离 | 关联交易 / 财务风险 |
| 乐视网 | 2018 | 持续经营能力存疑、连续亏损、经营现金流长期为负 | 持续经营 |
| 天神娱乐 | 2018 | 大额商誉减值风险、商誉占净资产比例畸高 | 财务风险 |
| 贵州茅台 | 2018 | **正常对照**（用于验证系统不误报健康企业） | 误报率控制 |

> 说明：上述案例均使用**公开披露信息**作为方法论验证样本，系统不对任何上市公司作出定性结论。
> 系统输出的风险条目按 formal、pending、excluded 分层；pending 对外显示为**待复核提示**，须由专业人员复核。

### 1.4 现有工具的不足

- **通用大模型直接问答**：能读文本，但数字会算错、会编造法规条款、没有稳定产物，不可审计；
- **单一规则引擎**：阈值写死、无法理解披露语境的语义差别（如"无重大关联交易"被误判为有风险）；
- **通用 OCR / 文档解析工具**：只能提取文本，不能形成风险判断与合规结论；
- **人工 Excel 底稿**：准确但不可扩展，且不同人做出的底稿结构不统一。

本项目要做的，是**把"大模型的语义理解能力"与"审计专业规则、确定性护栏、合规门禁"组合起来**，
产出一份可追溯、可复核、措辞审慎、结构稳定的审计风险初筛底稿。

### 1.5 工程可用性痛点（真实运行暴露并已修复）

系统在**真实年报实测**中暴露出四类"演示级"缺陷，均已定位根因并修复，构成"拟解决问题"的工程一侧：

| # | 真实表现 | 根因 | 修复 |
|---|---|---|---|
| 1 | 综合研判模式上传年报后成片"未检测出/未获取" | 预处理钩子只挂在主分析路径，`_run_synthesis_stages()` 三段串跑**不经过该门禁** | 在综合研判内部先跑一次预处理并注入预跑轨迹/台账（`agent.py`） |
| 2 | 报表字段大面积缺失 | 摘录窗口过窄（仅 17,790 / 176,691 字符）+ 回填字段仅 14 个 | 摘录改按报表关键词选页 + 80,000 字符上限；回填扩展到 63 个字段 |
| 3 | 产物名为「未知公司_IX_*」，Z/M 模型误判"缺少本期期间" | 公司名/报告期完全依赖 LLM 抽取，17 万字符里易漏 | 新增 `report_identity.py` 确定性识别 + 后端三处非覆盖兜底 |
| 4 | 现金流量表三个字段整段漏检 | 行首附注写成 `59(f)`，旧正则只肯跳过纯数字附注号 | `_row_pair` 正则放宽为 `(?:\d+(?:\([a-z]\))?\s+)?` |

> 说明：这四类问题的共同点是"**结构与工程问题**"而非模型能力问题——通过确定性规则与链路补全即可根治，
> 处理方式与本项目"确定性算法否决 LLM 幻觉"的一贯设计思路一致。

## 二、项目框架

### 2.1 总体设计思路

一句话：**让 AI 负责理解与表达，让代码负责计算与守住底线。**

- AI（大模型）擅长：理解年报自然语言、跨章节关联、生成可读的分析文字；
- 代码擅长：精确数值计算、严格的消息协议、稳定的文件产出、可复现的规则判定。

因此系统采用"**智能体自主调用工具链 + 确定性后处理兜底 + 合规硬门禁**"的组合架构：
LLM 在工具链中自由决策分析路径，但所有数字来自工具、所有产物由系统生成、
所有结论必须带法规依据与"AI 辅助生成"声明。

### 2.5 为什么选择"辩论式多智能体"而不是"全并发多智能体"

这是一个**主动的设计取舍**，也是本项目最需要向评审说明的一点：

**候选方案 A（全并发）**：把财务、合规、监管、行业等维度拆成多个独立 Agent 并行跑，最后汇总。
优点是吞吐高；缺点是——审计判断的特点是**维度之间存在强依赖与交叉验证关系**。
例如"经营现金流/净利润 < 0.5"这条财务异常，是否构成风险，取决于合规维度里"是否存在关联方资金占用"
以及监管维度里"是否有类似模式的历史处罚案例"。若各 Agent 完全并行、互不通信，
汇总层拿到的是彼此孤立的结论，无法形成"证据链闭环"，反而会放大误报。

**本项目方案 B（单主智能体 + 辩论复核）**：主体由一个 ReAct 智能体按固定审计逻辑依次调用 16 个工具，
保证跨维度的因果链在同一上下文中传递；分析完成后，再让三个角色
（**风险关注方** → **风险否定方** → **裁判仲裁**）对风险台账进行对抗式复核，
用于抑制"过度报警"与"漏报"两种偏差，并把仲裁结论回写风险等级（保留原始等级可追溯）。

**结论**：我们不是在追"多 Agent"的概念，而是让多 Agent 只承担它最有价值的那一环——
**对抗式复核**。既保证了证据链的连贯性，又获得了多智能体制衡带来的准确性提升。
综合研判模块内部仍对相互独立的两个阶段（财务、合规）使用 `asyncio.gather` 并行，兼顾效率。

### 2.6 任务模块与工具裁剪

为避免"每次都给模型 16 个工具、让它自己挑"带来的慢与错，系统按用户意图做**模块裁剪**：

| 模块 | 触发意图 | 工具集规模 | 行为 |
|---|---|---|---|
| 财务健康度诊断 | 财务/指标/报表相关 | 7 | 全流程 + 辩论 + 导出 |
| 合规与经营风险扫描 | 合规/披露/审计意见相关 | 4 | 全流程 + 辩论 + 导出 |
| 综合研判 | 综合分析/全面评估 | 三段串跑 | 财务 ∥ 合规 → 综合 + 辩论 + 导出 |
| 行业风向研判 | 行业/赛道相关 | 3 | 行业维度分析 + 导出 |
| 智能投资参考卡 | 投资参考/参考卡 | 7 | **轻量路径**（不辩论/不评分/不导出） |
| 行业风向标 | 行业风向标 | 2 | **轻量路径** |

## 四、解决方案与创新点

### 4.1 五大风险维度模型

把审计风险归纳为五个可量化判定的维度：

| 维度 | 通俗解释 | 关键判定信号（举例） |
|---|---|---|
| 财务风险 | 报表数字可能不实 | 经营现金流/净利润长期 < 0.5；应收账款增速远超营收；存贷双高 |
| 关联交易 | 和自己人做生意 | 关联采购占比 > 30%；大股东股权质押 > 70% |
| 信披合规 | 该说的没说清楚 | 无理由变更会计政策；重大事项延迟披露；必备章节缺失 |
| 持续经营 | 公司可能撑不下去 | 连续两年扣非亏损；净资产为负；经营现金流连续为负 |
| 监管处罚 | 有被处罚的苗头 | 与已处罚公司的造假模式相似；连续更换会计师事务所 |

系统同时内置**行业基准阈值**，判断某公司指标是否异常时与其所在行业的正常水平比较，
而不是对所有公司一刀切。

### 4.2 四种前沿智能体范式（全部落地）

| 范式 | 落地方式 | 解决的问题 |
|---|---|---|
| **RAG 知识增强检索** | 识别到风险后检索法规知识库（ChromaDB 向量检索，TF-IDF 回退），做到"每个结论都有法规依据" | 大模型编造法规条款 |
| **思维链推理（CoT）** | 每条风险输出五步：【数据发现】→【指标异常】→【法规依据】→【案例对照】→【风险判定】 | 黑盒结论、不可解释 |
| **多智能体辩论复核** | 风险关注方 → 风险否定方 → 裁判仲裁，仲裁结论回写风险等级（保留原始等级） | AI 过度报警或漏报 |
| **固定工具链 + 分级门禁** | 智能体按审计逻辑调用工具；确定性门禁保证"先校验后计算"，漏做自动补救 | 模型跳步、顺序错乱 |

### 4.3 与通用大模型问答的本质区别

| 对比项 | 通用大模型直接问答 | 本系统 |
|---|---|---|
| 数字来源 | 模型生成，可能算错 | 全部来自工具计算，模型只负责引用 |
| 法规依据 | 可能编造条款号 | 从知识库检索原文并引用 |
| 结论措辞 | 可能给出定性判断 | 固定为"待复核提示，尚未作出实质合规认定"，`confirmed_issue_count=0` |
| 产物 | 一段文字 | PDF 专项+综合报告、Excel 九表底稿、三张图表 |
| 可复现性 | 每次不同 | 产物结构固定、有版本号、有测试与离线验收 |
| 合规声明 | 无 | **fail-closed 硬门禁**：无"AI 辅助生成"声明则拦截不落盘 |

### 4.4 创新点小结

1. **"LLM 说、代码算"的双轨架构**：模型自由分析，但所有数字、等级、产物由确定性代码兜底与把关；
2. **辩论式复核的工程化**：不以"多 Agent"为卖点堆数量，而是把对抗式复核嵌入产物生成链路，
   仲裁结果直接影响 PDF/Excel 中的风险等级；
3. **确定性与概率性的混合护栏**：P9 合规勾稽恢复、P10 单位量级补偿、P11 归母口径兜底、
   评分代跑、工具顺序 fail-closed 门禁，每一条都对应一个实测缺陷；
4. **合规即代码（Compliance as Code）**：把竞赛手册 6.2.3 的伦理要求写进 `domain_guard`，
   让"必须含 AI 生成声明"成为不可绕过的程序断言，而不是文档里的一句承诺；
5. **可降级设计贯穿全栈**：ChromaDB → TF-IDF、AsyncSqliteSaver → MemorySaver、
    PostgreSQL → SQLite、S3 → 本地磁盘、ECharts → 表格，
   **任何单点不可用都不会让系统不可用**。

## 六、效果评估

### 6.1 评估设计

采用**合成集 + 盲测集双轨**评估，分别验证"规则正确性"与"泛化能力"：

| 数据集 | 用途 | 用例数 | 设计原则 |
|---|---|---|---|
| 合成集 | 验证规则与阈值实现是否与设计一致 | 22 | 构造覆盖五大维度、边界值与正常对照 |
| 盲测集 | 验证未参与阈值设计的真实公开案例 | 5 | 康得新/康美药业/乐视网/天神娱乐 + 贵州茅台正常对照 |

Precision 与 Recall 分别从**误报**与**漏报**两个方向独立统计
（Precision 分母为系统实际告警数，Recall 分母为标注风险数），盲测集与合成集分开报告，
避免循环验证。

### 6.2 评估结果

| 数据集 | 用例数 | Precision | Recall | F1 | 备注 |
|---|---|---|---|---|---|
| 合成集 | 22 | 1.00 | 1.00 | 1.00 | 正常用例误报 0/2；工具模式平均响应 0.001s |
| 盲测集 | 5 | 1.00 | 1.00 | 1.00 | 正常对照正确 1/1 |
| vs 单规则基线 | - | - | **+92.3pp** | - | 召回率提升（百分点） |

### 6.3 诚实说明（局限与自省）

- **样本量小**：5 例盲测不足以支撑统计显著性结论，结果用于验证"机制方向正确"，
  而非宣称"已具备生产级准确率"；
- **评估口径为风险维度级**：衡量的是"是否识别出正确维度的风险"，不等同于"风险等级完全一致"；
- **真实年报的复杂性**：评估样本经过结构化整理，真实 PDF 的表格排版、扫描件质量、
  跨页表格等情况会更复杂；
- **后续计划**：把盲测集扩到 50~100 例，引入误报率（FP rate）与业务损失加权指标，
  并建立长期跟踪机制。

## 七、伦理与合规

### 7.1 必须包含的声明

系统所有对外输出（PDF 报告、Excel 底稿、图表、界面结论区）**必须包含"AI 辅助生成"声明**，
由 `domain_guard.assert_disclaimer_present()` 作为**硬门禁**在导出前校验，
缺失则拦截、不落盘。这条要求在竞赛手册 6.2.3 中有明文规定，本项目把它实现为**程序断言**而非文档承诺。

### 7.2 审慎措辞（避免未经核实的负面评价）

| 措施 | 实现 |
|---|---|
| 不作定性结论 | 披露检查固定输出 `compliance_conclusion="待复核提示，尚未作出实质合规认定"` |
| 不声称发现造假 | 输出 `confirmed_issue_count=0`，所有问题状态为 `needs_review` / `candidate` |
| 风险条目均标注待复核 | `formal_status="candidate"`、`pending_verification=True`、`verification_status="待复核"` |
| 勾稽失败不直接定级 | 数据校验失败只生成 `level="待定级"`、`confidence=None` 的候选条目 |
| 保留原始等级 | 辩论仲裁回写风险等级时保留 `original_level` 字段，全过程可追溯 |
| 明确免责 | 界面与产物均有免责声明："仅供审计参考与风险提示，不构成最终审计意见或投资建议" |

### 7.3 数据来源合法性与开源合规

- 知识库 41 个文本全部来自**公开法规、准则与公开案例**，来源与授权逐一记录于 `DATA_SOURCES.md`；
- 案例样本使用**已公开披露**的上市公司信息，仅用于方法论验证，不对公司作评价或定性；
- 全部依赖均为开源组件（FastAPI / LangGraph / ChromaDB / reportlab / openpyxl / matplotlib / ECharts 等），
  ECharts 采用本地 vendor 形式分发，不依赖外部 CDN；
- 不训练、不微调任何模型，仅通过 API 调用公开模型服务，规避训练数据版权风险。

### 7.4 人机协同定位

系统定位是**审计师的初筛助手**，不是替代审计师：
产物结构上明确区分"已核验事实"与"待复核提示"，每个风险条目都给出建议的核查程序，
最终判断权与责任仍在具备资质的专业人员。后续规划中的"复核人/复核意见/复核时间"字段，
将进一步把这一分工固化到工作流中。

### 7.5 信息安全

- 写操作接口可用 `APP_API_KEY` 强制鉴权；用户接口使用独立的会话令牌机制；
- 上传文件做扩展名白名单、100MB 大小上限、分块流式落盘、超限删除半成品、文件名清洗；
- 异常信息脱敏：对外只回通用错误提示，路径、密钥与堆栈只写服务端日志；
- 交付打包脚本对 `.env`、数据库、检查点、内部运行结果做禁止项拦截，防止密钥随包外泄。
