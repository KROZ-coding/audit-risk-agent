# 根治「审计仲裁未完成（系统补全重试失败）」方案

## 1. 问题现象

在「综合研判」模式下，Agent 第三阶段仅调用 `calculate_comprehensive_score` 与 `search_regulations` 两个工具后，多智能体辩论的仲裁人给出「需补充 / 需重新分析」的 verdict，系统补全重试失败，触发 50f 真阻断（现已改为降级导出）。

## 2. 根因分析

综合研判采用三段串跑：

1. 第一阶段 `financial`：跑 `validate_financial_data`、`calculate_financial_indicators` 等
2. 第二阶段 `compliance`：跑 `check_disclosure_compliance`、`identify_audit_opinion`、`search_regulations` 等
3. 第三阶段 `synthesis`：基于前两段结论做交叉验证、形成最终风险台账

第三阶段 LLM 的问题：

- **工具子集被裁剪**：`MODULE_TOOLS["synthesis"]` 不含 `validate_financial_data` / `calculate_financial_indicators` / `check_disclosure_compliance`，LLM 无法自己补跑
- **只能看到文本摘要**：`build_stage_payload` 只把前两段的文本摘要注入第三阶段，LLM 容易遗漏关键结构化证据（如 `alerts`、`failed_checks`、`issues`）
- **生成的 risk_json 证据链薄弱**：风险条目缺少与真实工具结果的直接关联，仲裁人依据「证据不足」判「需补充」

## 3. 根治目标

让第三阶段生成的 `risk_json` 中，**每条风险条目都能追溯到前两阶段工具的真实结构化输出**，从而仲裁人有充分依据裁定「通过」。

## 4. 实施方案（1 + 2 + 4）

### 4.1 方案 1：强化第三阶段提示词，强制引用证据

**修改文件：** `src/agents/pipeline.py`

**修改点：**

- 在 `STAGE_INSTRUCTIONS["synthesis"]` 中明确要求：最终风险台账的每条风险必须引用前两阶段工具的具体输出
- 在 `CROSS_VALIDATION_INSTRUCTION` 中要求交叉验证矩阵必须体现「财务诊断发现」「合规扫描发现」与工具输出的对应关系

**预期效果：**

- 从 prompt 层约束 LLM 不写空泛 evidence
- 与方案 2 配合，LLM 有证据可看、有格式要求可遵循

### 4.2 方案 2：把前两段核心工具结构化结果注入第三阶段

**修改文件：** `src/agents/pipeline.py`

**修改点：**

- 扩展 `build_stage_payload` 接口，允许传入前两段的工具结果字典 `prior_tool_results`
- 当 `module == "synthesis"` 时，把以下工具结果以结构化 JSON 文本形式追加到用户消息：
  - `calculate_financial_indicators`
  - `validate_financial_data`
  - `check_disclosure_compliance`
  - `identify_audit_opinion`
- 在 `src/main.py` 的 `_run_synthesis_stages` 中，把 `stage_ledger_entries` 转换为 `prior_tool_results` 并传入

**预期效果：**

- 第三阶段 LLM 直接看到真实指标异常、勾稽不平、披露缺失、审计意见等结构化证据
- 生风险台账时 naturally 引用这些证据

### 4.3 方案 4：在 `_post_process` 中用真实工具结果自动补全 risk_json 证据

**修改文件：** `src/agents/agent.py`

**修改点：**

- 在 `_post_process` 的辩论前阶段，新增 `_backfill_risk_evidence(risk_json, tool_results)`
- 解析 `tool_results` 中的核心工具输出，提取：
  - `calculate_financial_indicators.alerts`
  - `validate_financial_data.data_validation.results`
  - `check_disclosure_compliance.issues`
  - `identify_audit_opinion.opinion_type`
- 遍历 `risk_json["risk_details"]`，对 `evidence` 为空或太泛的条目：
  - 按维度/标题关键词匹配系统证据
  - 匹配成功则把系统证据写入 `evidence`，并标记 `system_backfilled: true`
  - 匹配失败且 confidence >= 0.5 则降级为 `confidence = 0.4`，标记 `pending_verification`

**预期效果：**

- 系统兜底：即使 LLM 没按提示词引用证据，后处理也会补上
- 仲裁人看到的台账永远有可追溯的证据链
- 无法补全的条目会被降级为「待核实」，不会误导用户

## 5. 配合已做的兜底策略

此前已把「仲裁未完成 → 真阻断零产出」改为「强可见警告 + 继续导出完整产物」。即使方案 1+2+4 实施后仍有偶发仲裁失败，用户也能拿到完整 PDF/Excel/图表，只是带警告。

## 6. 验证计划

1. 单元测试：`tests/test_data_validator.py`、`tests/test_financial_calculator.py` 不回归
2. 集成测试：跑一份 synthesis 模式的真实年报，检查：
   - 第三阶段用户消息中是否包含核心工具结构化结果
   - 生成的 `risk_json` 中 `risk_details[i].evidence` 是否非空
   - 仲裁 verdict 是否为「通过」

## 7. 风险与回退

| 风险 | 应对措施 |
|---|---|
| 注入文本过长挤占上下文 | 只注入核心字段，每个工具结果截断到 3000-4000 字符 |
| 证据匹配错误 | 标记 `system_backfilled: true`，让人工知道是系统补的 |
| LLM 仍然不引用证据 | 启用备选方案 3：把核心前置工具加回 `MODULE_TOOLS["synthesis"]` |
| 仲裁人仍判「需补充」 | 保留已关闭的真阻断兜底，输出完整产物 + 警告 |

## 8. 修改文件清单

- `src/agents/pipeline.py`：方案 1 + 方案 2
- `src/main.py`：方案 2 的数据透传
- `src/agents/agent.py`：方案 4
