> 版本：v5.3 GA  
> 软件包版本：5.3.0  
> 报告定位：上市公司年报风险筛查智能体的技术实现与验证说明  
> 事实核对日期：2026-09-19  
> 规则、数据和结果契约：2026-09-v3 / 1.0 / 2.0

## 摘要

本报告说明“上市公司年报风险智能识别系统”v5.3 GA 的业务目标、智能体架构、财务分析方法、审计证据链、风险采信规则和多产物发布机制。系统面向上市公司年报、半年报及相关财务材料，将自然语言分析任务拆分为财务健康度诊断、合规与经营风险扫描、综合研判与交叉验证三个阶段，并以确定性工具承载事实提取、指标计算、报表勾稽和结果发布。

系统的核心结论是：大模型负责任务组织、跨文本理解和解释生成；Python 工具负责数据归一、财务计算和结构化校验；证据门禁负责区分正式采信风险与待复核事项；`report_snapshot` 负责统一 Web、PDF、Excel、TXT、JSON 和历史记录的底层事实。该设计使输出结果具备可复算、可回指、可降级和可复核的特征，避免把模型生成的自然语言直接等同于审计结论。

报告重点呈现与业务闭环直接相关的实现，包括六类财务指标、缺失数据处理、期间与单位控制、C2/C1 复核、风险证据门禁、公共文本净化和产物一致性。前端视觉实现仅作为交互入口说明，完整源码、配置、测试与部署脚本随 v5.3 软件包提供。

## 1. 项目概述与结论先行

### 1.1 项目名称与定位

项目名称为“上市公司年报风险智能识别系统”。系统面向年报、半年报及相关财务材料，提供从原始材料接收、报表事实提取、财务指标计算、披露筛查、法规检索、风险交叉验证到报告发布的完整分析链路。

系统的定位不是替代注册会计师出具审计意见，也不是根据模型分数直接认定企业存在违法、造假或错报。系统定位为：

> **以智能体组织分析任务，以确定性工具承载事实和计算，以证据门禁控制风险采信，以 Web 和多种产物交付可复核的年报风险筛查结果。**

### 1.2 系统解决的业务问题

传统年报初筛通常面临四类问题：

| 业务痛点 | 具体表现 | 本系统的解决方式 |
| --- | --- | --- |
| 信息量大 | 年报页数多，财务表格、附注、审计意见和重大事项分散 | 先解析并定位来源，再由分工明确的智能体阶段处理 |
| 数值判断不稳定 | 手工计算易出现单位、期间、分母和合并口径错误 | 指标和勾稽由 Python 确定性计算，保留公式和代入过程 |
| 文字结论难复核 | 单纯模型输出可能缺少页码、原文摘录和反向证据 | Fact、Evidence、MetricResult、RiskFinding 建立证据链 |
| 结果难以交付 | Web、PDF、Excel 可能出现数量、标题和结论不一致 | 终局 report_snapshot 作为所有产物的共同事实源 |

系统最终交付的不是一个孤立分数，而是由以下对象组成的分析结果：

```text
原始年报
  -> 可定位事实
  -> 可复算指标
  -> 可回指证据
  -> 风险候选与复核状态
  -> 正式采信风险 / 待复核事项
  -> 综合评分与交叉验证
  -> Web、PDF、Excel、TXT、JSON 和历史记录
```

### 1.3 核心技术结论

本系统最重要的设计不是“让模型写出更长的报告”，而是建立下面的责任分工：

| 责任 | 主要承担者 | 设计原因 |
| --- | --- | --- |
| 理解用户任务、组织分析阶段、调用工具 | LLM Agent | 适合处理自然语言任务和非结构化材料 |
| 文档解析、字段归一、公式计算、单位换算 | Python 工具 | 需要确定性、可复算和可测试 |
| 报表勾稽、证据绑定、风险分层、等级底线 | Python 后处理与门禁 | 不能让模型自行决定是否满足发布条件 |
| 阶段交接和综合解释 | Pipeline + LLM | 既保留业务上下文，又减少状态污染 |
| PDF、Excel、TXT 和网页发布 | 快照与导出层 | 所有产物必须来自同一批最终数据 |
| 人工复核边界 | 产品规则与报告措辞 | 系统只能提供筛查和核查线索，不替代审计判断 |

## 2. 业务流程设计

### 2.1 目标用户与使用场景

系统服务于以下使用场景：

- 审计前期或项目承接阶段，对上市公司年报进行快速风险筛查。
- 教学、竞赛和业务验证场景中，展示人工智能如何参与财务与合规分析。
- 财务、风控和研究人员需要把“异常数字”转成可继续核查的事项清单。
- 需要同时获得网页结果、结构化底稿和可归档报告的分析任务。

### 2.2 一条年报分析任务的业务闭环

```text
1. 接收材料与分析要求
   ↓
2. 解析文本、页码、期间、单位、合并范围和报告身份
   ↓
3. 校验基础事实，登记 Fact
   ↓
4. 计算指标、勾稽关系、量化筛查模型
   ↓
5. 检查披露章节、审计意见、重大事项和监管线索
   ↓
6. 财务阶段输出健康度诊断
   ↓
7. 合规阶段输出披露与经营风险扫描
   ↓
8. 综合阶段基于前两阶段真实结果交叉验证
   ↓
9. C2 语义复核与 C1 关注方/否定方/仲裁
   ↓
10. 证据门禁、风险分层、评分和公开文本净化
    ↓
11. 生成 Web、PDF、Excel、TXT、JSON 和历史记录
```

每一步都对应一个可观察的业务状态或代码责任，不把完整流程隐藏在一条不可解释的模型调用中。

### 2.3 分析结果的三种状态

系统明确区分“发现”“采信”和“待复核”：

| 状态 | 业务含义 | 是否计入正式风险统计 | 是否可作为最终结论 |
| --- | --- | --- | --- |
| 正式采信 | 有可回指且已核验的证据，并通过结构化门禁 | 是 | 仍需按审计边界理解，不能替代审计意见 |
| 待复核 | 有线索但证据、口径、语义或适用条件尚未闭环 | 否 | 只能作为人工核查清单 |
| 排除项 | 重复项、失效项、内部兼容项或不能成立的候选 | 否 | 不对外作为风险展示 |

这一区分解决了“候选风险数量很多，所以系统认为风险很高”的常见误读。候选数量、正式风险数量和综合评分分别保存，互不替代。

## 3. 总体智能体架构

### 3.1 分层架构

```text
Web 演示层
  src/web/index.html
  上传、请求、SSE 进度、结果卡片、产物链接和历史查看

接口与任务层
  src/main.py
  FastAPI 路由、上传安全、同步/流式运行、任务上下文和评估接口

编排层
  src/agents/pipeline.py
  三阶段定义、阶段指令、摘要交接、交叉验证要求和进度边界

智能体层
  src/agents/agent.py
  LangGraph ReAct、工具台账、消息窗口、复核调用、后处理和发布触发

确定性工具层
  src/tools/*.py
  PDF 解析、财务指标、勾稽校验、披露检查、法规检索、风险模型和评分

事实与发布层
  src/core/result_contract.py
  src/core/report_snapshot.py
  src/core/report_publication.py
  结构化记录、证据绑定、快照、文件清单和产物一致性

存储与知识库层
  src/storage/、src/local_knowledge.py、src/local_storage.py
  业务数据、检查点、离线知识库、本地产物和历史记录
```

分层的核心价值是责任边界清楚：Agent 负责调度，工具负责计算，门禁负责采信，快照负责统一，导出层负责表达。

### 3.2 端到端数据流

```text
上传文件 / 用户文本
  -> 文件类型、大小、路径和来源哈希检查
  -> PDF/Word/Excel/HTML/PPTX/TXT 解析
  -> 报告身份识别和事实登记
  -> 财务预处理与核心工具调用
  -> 三阶段 Agent 流程
  -> 风险复核与门禁
  -> report_snapshot
  -> publication / manifest
  -> Web、PDF、Excel、TXT、JSON、历史
```

### 3.3 模型与代码的协同方式

模型可以做的事情：

- 识别用户要分析的模块和重点问题。
- 根据阶段指令选择合适的工具。
- 结合事实、指标和法规检索结果组织解释。
- 对财务发现与合规发现进行语义层面的交叉验证。
- 生成面向业务人员可读的核查建议。

模型不能单独决定的事情：

- 不能把缺失数值填成零或中性值。
- 不能修改确定性计算出的指标和公式。
- 不能无证据新增正式风险。
- 不能把中期数据强行解释为完整年度数据。
- 不能把量化模型的筛查信号写成破产、造假、违法或审计结论。
- 不能直接决定所有产物的最终数量和身份。

### 3.4 Agent 配置原则

当前配置文件为 `config/agent_llm_config.json`，主要参数如下：

| 配置项 | 当前值或规则 | 作用 |
| --- | --- | --- |
| 主模型 | `deepseek-v4-flash` | 兼顾结构化输出、响应速度和演示成本 |
| temperature | `0.3` | 降低同一输入的随机变化 |
| top_p | `0.9` | 保留必要的语言表达能力 |
| max_completion_tokens | `8192` | 容纳结构化报告和解释 |
| timeout | `600` | 为长年报和工具链留出时间 |
| 工具数量 | 16 个注册工具 | 覆盖解析、财务、合规、模型、轻量模块和图表前的分析能力 |

提示词还规定了工具调用顺序、证据要求、半年度报告限制、法规检索次数、缺失值处理、风险措辞边界和 AI 生成声明。这些规则是业务约束，不是让模型自由发挥的写作要求。

## 4. 三阶段智能体编排

### 4.1 阶段职责

综合研判入口采用固定顺序：财务健康度诊断 → 合规与经营风险扫描 → 综合研判与交叉验证。

| 阶段 | 主要回答的问题 | 主要工具 | 明确不负责的内容 |
| --- | --- | --- | --- |
| 财务健康度诊断 | 报表数据是否自洽，盈利、运营、偿债、成长和现金流质量如何 | `validate_financial_data`、`calculate_financial_indicators`、`calculate_risk_models` | 不直接判断披露违法，不承担监管处罚结论 |
| 合规与经营风险扫描 | 披露是否完整，审计意见和监管线索如何，行业经营环境有哪些风险 | `check_disclosure_compliance`、`identify_audit_opinion`、`search_regulations`、行业工具 | 不重复计算上一阶段的基础财务指标 |
| 综合研判与交叉验证 | 两个维度是否相互支持或相互矛盾，哪些事项可采信，最终如何分层 | 核心工具结构化结果、`calculate_comprehensive_score`、复核链 | 不在模型中直接生成 PDF/Excel |

### 4.2 固定顺序和进度语义

源码中的 `SYNTHESIS_STAGES` 是阶段顺序的单一来源：

```python
# src/agents/pipeline.py
SYNTHESIS_STAGES = [
    ("financial", "第一阶段 · 财务健康度诊断", 5, 35),
    ("compliance", "第二阶段 · 合规与经营风险扫描", 35, 65),
    ("synthesis", "第三阶段 · 综合研判与交叉验证", 65, 95),
]
```

运行层对前两个互不依赖的阶段使用 `asyncio.gather` 并行执行，以压缩等待时间；第三阶段必须等前两阶段的摘要和核心工具结果准备完成后再运行。对外发布仍按“财务健康度诊断 → 合规与经营风险扫描 → 综合研判与交叉验证”的稳定顺序发出阶段锚点和进度事件，因此性能优化不会改变业务流程语义。前端只负责展示服务端事件，不重新推断业务阶段。流式事件在展示层按阶段和步骤去重，同一事件重复到达时更新原条目并保留历史最大进度值，因此阶段名称不会重复、百分比不会倒退。

### 4.3 阶段交接为什么采用摘要加结构化结果

三个阶段不共享完整 LangGraph 状态，而是通过以下两类输入交接：

1. 上一阶段的最终分析摘要，用于保留业务语境。
2. 财务、校验、披露、审计意见、模型和评分等工具的结构化投影，用于让第三阶段引用真实证据。

这样做有四个好处：

- 阶段状态隔离，前一阶段的工具调用不会无条件污染后一阶段。
- 摘要不依赖消息窗口，早期阶段不会因为滑窗被裁掉。
- 工具结果中重复的原文和事实表可以省略，指标状态、限制、检查结果和证据编号保留。
- 某阶段失败时仍会传递“该阶段没有有效结论”的显式信号，第三阶段不能把失败误解为没有风险。

关键交接函数为 `src/agents/pipeline.py::build_stage_payload`。其逻辑可概括为：

```python
def build_stage_payload(base_payload, module, marker,
                        prior_summaries, prior_tool_results=None):
    messages = list(base_payload.get("messages", []))
    original = messages[-1]["content"]

    parts = [marker, STAGE_INSTRUCTIONS[module]]
    parts.extend(format_summary(name, text)
                  for name, text in prior_summaries)

    if module == "synthesis":
        for tool_name in CORE_TOOLS:
            result = prior_tool_results.get(tool_name)
            if result:
                parts.append(summarize_tool_result(result,
                                                   tool_name=tool_name))
        parts.append(CROSS_VALIDATION_INSTRUCTION)

    parts.append("【原始分析请求与数据】\n" + str(original))
    return {**base_payload,
            "messages": messages[:-1] + [{"role": "user",
                                           "content": "\n".join(parts)}]}
```

上面代码是核心逻辑的压缩展示，完整实现还包括 LangChain 消息对象兼容、非法 JSON 处理、摘要长度控制和失败阶段提示。

### 4.4 第三阶段的交叉验证契约

第三阶段必须输出交叉验证矩阵，每条候选风险至少包含：

| 字段 | 含义 |
| --- | --- |
| 风险编号 | 与最终风险台账稳定对应 |
| 风险描述 | 具体描述事项，不使用空泛的“存在风险” |
| 财务诊断发现 | 直接引用指标、校验或模型工具的具体结果 |
| 合规扫描发现 | 直接引用披露检查、审计意见或法规检索结果 |
| 验证状态 | 相互印证、存在矛盾、单方发现 |
| 置信度 | 由证据状态和验证结果约束，不由文字长度决定 |

状态约束如下：

- 相互印证：两个阶段均发现指向同一事项的证据，置信度可以上调。
- 存在矛盾：两个阶段结论或口径不一致，必须列为进一步核实事项。
- 单方发现：只有一个阶段存在证据，置信度不得高于 0.7。
- 无法回指工具证据：置信度不得高于 0.5，不能直接进入正式采信层。

## 5. 工具体系与业务逻辑

### 5.1 工具与业务问题映射

| 工具 | 业务作用 | 输出给谁 |
| --- | --- | --- |
| `parse_pdf_report` | 读取年报文本、页码和源文件信息 | 财务阶段、合规阶段和证据登记 |
| `validate_financial_data` | 资产负债表、现金流有限勾稽、未分配利润一致性 | 财务阶段、证据门禁 |
| `calculate_financial_indicators` | 确定性计算盈利、运营、偿债、成长、现金流和资产质量指标 | 财务阶段、综合阶段、指标视图和产物 |
| `calculate_risk_models` | 计算 Z-Score、M-Score 或明确记录不适用 | 财务阶段、综合阶段 |
| `check_disclosure_compliance` | 筛查必要章节、重大事项、会计政策和交叉引用 | 合规阶段、综合阶段 |
| `identify_audit_opinion` | 识别审计意见和可信度影响信号 | 合规阶段、综合阶段 |
| `search_regulations` | 查找适用法规和监管依据 | 合规阶段、综合阶段 |
| `search_regulatory_inquiries` | 获取公司问询、处罚或监管动态线索 | 合规阶段、轻量模块 |
| `calculate_comprehensive_score` | 汇总可用维度，生成评分、分解和限制 | 综合阶段和快照 |
| `compare_multi_year` | 进行多年趋势和期间对比 | 财务阶段和产物 |
| `batch_analyze_companies` | 对多家公司执行批量分析入口 | 批量业务 |
| `investment_advisor` | 在独立轻量模块中生成风险参考卡 | 投资参考模块 |
| `industry_outlook` | 获取行业事件、景气度和传导线索 | 行业展望模块 |
| `generate_risk_heatmap` | 生成正式风险与待复核提示的可视化 | 系统后处理 |
| `generate_radar_chart` | 生成财务维度对比图 | 系统后处理 |
| `generate_trend_chart` | 生成多年趋势图 | 系统后处理 |

工具结果首先进入工具台账和结构化契约，再进入模型上下文。工具调用不是“调用完就丢掉的函数返回值”，而是后续证据绑定和发布一致性的输入。

### 5.2 输入解析与报告身份

系统支持 PDF、Word、Excel、CSV、HTML、PPTX、TXT 和 Markdown 等输入。输入处理包含：

- 文件扩展名白名单和单文件大小限制。
- 分块读取并计算源文件 SHA-256。
- 文件名清洗和工作目录约束。
- PDF 页码标记，便于证据回指。
- 报告期间、公司名称、股票代码、行业、单位、合并范围和审计意见的确定性识别。
- 输入文本长度限制，避免超大正文直接进入上下文。

报告身份由 `src/utils/report_identity.py` 进行确定性识别，并在模型结果缺失或不可信时提供兜底。身份字段包括公司、股票代码、行业、报告期、报告类型、审计意见、会计准则、合并范围和源文件指纹。

### 5.3 财务事实与单位处理

财务字段不是简单的键值对。每个事实同时携带：

- 原始字段和原始值。
- 规范化数值、单位和币种。
- 报告期间或时点。
- 合并范围和会计口径。
- 来源文件、页码、定位和原文摘录。
- 提取方式和来源状态。

系统区分流量数据和时点数据：收入、利润、成本、经营现金流属于期间流量；现金、应收、存货、资产和负债属于时点余额。中期报告不能把期初余额、上年同期余额和本期流量随意拼接。

金额单位先归一化再计算，导出时再按展示规则格式化。单位换算不是风险判断，单位和期间元数据缺失时，结果会显示限制而不是静默采用默认值。

## 6. 财务分析逻辑

### 6.1 指标分组与计算范围

当前指标视图按照以下顺序组织：

1. 盈利能力。
2. 营运能力。
3. 偿债能力。
4. 成长能力。
5. 现金流质量。
6. 资产质量与审计关注。

源码当前支持 41 个指标结果键：其中 39 个由固定计算段定义，归母净利润同比和扣非归母净利润同比根据输入字段动态生成。具体任务不会机械输出全部指标，而是根据事实、期间、合并范围和分母有效性动态形成 `metric_results`。已计算指标进入能力分组，缺失输入、零分母、负基期或不可比期间的指标进入状态说明；相关字段全部没有披露时不生成空条目。

### 6.1.7 指标输出契约与分组代码

指标结果的公共展示顺序由 `src/tools/indicator_view.py::CAPABILITY_GROUPS` 固定，当前顺序为“盈利能力 → 营运能力 → 偿债能力 → 成长能力 → 现金流质量 → 资产质量与审计关注”。展示层只读取计算层的 `metric_results` 和 `evidence`，不在 Web、PDF 或 Excel 中重新计算。其核心结构如下：

```python
CAPABILITY_GROUPS = (
    ("盈利能力", (...)),
    ("营运能力", (...)),
    ("偿债能力", (...)),
    ("成长能力", (...)),
    ("现金流质量", (...)),
    ("资产质量与审计关注", (...)),
)

for label, metric_ids in CAPABILITY_GROUPS:
    items = [by_id[key] for key in metric_ids
             if key in by_id and by_id[key].get("value") is not None]
    if items:
        groups.append({"label": label, "metrics": items})
```

单项指标同时保留 `metric_id`、中文名称、公式、输入值及单位、期间与合并范围、代入过程、结果、阈值、状态、原因和 `evidence_ids`。因此页面上看到的“未计算”不是空白或默认值，而是对数据条件不满足的可追踪说明。

### 6.2 缺失数据规则

指标计算遵守三个规则：

- 缺失不等于 0。
- 分母为 0、期间不可比或来源不完整时，不生成伪造比例。
- 相关字段全部缺失时不生成无意义的“未计算”指标；只要至少一个字段存在，就保留指标并明确列出缺失字段。

当前 `src/tools/financial_calculator.py::calculate_financial_indicators` 的核心逻辑如下：

```python
def add(metric_id, name, formula, keys, value, **kwargs):
    only_if_any_input = kwargs.pop("_only_if_any_input", False)
    missing = [key for key in keys if values.get(key) is None]

    # 所有相关源字段均未披露时，不生成无意义条目。
    if only_if_any_input and len(missing) == len(keys):
        return None

    # 部分字段存在时保留指标，并把缺失字段写入状态和原因。
    if value is None and missing:
        kwargs["status"] = "insufficient_data"
        kwargs["reason"] = "缺少有效输入：" + "、".join(missing)

    metric = _metric(metric_id, name, formula, values, facts_by_key,
                     keys, value, period=period, scope=scope,
                     metric_lookup=metric_lookup, **kwargs)
    metrics.append(metric)
    if value is not None:
        indicators[metric_id] = metric["value"]
```

例如现金/短期借款、经营现金流/总负债、坏账准备/应收账款等指标：

- 两个字段都没有时不生成空指标。
- 只有一个字段时保留指标，显示缺失字段和不能计算的原因。
- 两个字段都存在且口径一致时正常计算。
- 不用 0、中性值或模型猜测替代缺失数据。

Web 指标视图、PDF、Excel 和 TXT 均从同一份指标结果读取，因此不会出现页面和底稿使用不同算法的问题。

### 6.3 指标解释边界

指标阈值是内部筛查参考，不是监管红线。例如应收/营收比上升、经营现金流/净利润偏低或商誉占比较高，只表示需要结合附注、客户结构、账龄、减值测试和审计程序进一步核查。

系统要求结论尽量遵循：

```text
具体事实或数值
  -> 同口径比较
  -> 异常或变化说明
  -> 可能的业务解释
  -> 建议的核查程序
```

禁止直接从单项指标跳到确定性结论。比如“现金流/净利润低于筛查阈值”只能形成回款、利润质量或营运资金的核查方向，不能直接等同于收入确认不当。

### 6.4 财务勾稽校验

`src/tools/data_validator.py` 提供三类校验：

1. 资产负债表：总资产是否等于总负债加净资产。
2. 现金流有限勾稽：经营现金流、净利润、折旧、摊销和营运资本变动之间是否能形成有限解释。
3. 未分配利润一致性：期初、期末未分配利润与归母净利润、分红和已披露其他变动是否相互支持。

缺少字段时，系统返回 `limited_check`、`insufficient_data` 或待复核状态，不反算出一个看似完整的结果。现金流勾稽明确是有限检查，不是完整现金流审计。

## 7. 合规、审计意见与经营环境分析

### 7.1 披露检查

`src/tools/disclosure_checker.py` 负责文本层面的筛查，主要覆盖：

- 定期报告必要章节。
- 重大事项和风险因素的文本覆盖。
- 会计政策及会计估计变更。
- 关联方、担保、诉讼和重大合同等事项的交叉引用。
- 审计意见、关键审计事项和报告正文之间的关联。

“关键词没有出现”不等于法律意义上的“没有披露”，“工具没有发现”也不等于“企业一定合规”。因此输出统一使用“筛查结果”“待复核提示”和“在实际检索范围内未发现”等限定语。

### 7.2 审计意见

系统识别审计意见类型、强调事项、持续经营重大不确定性和关键审计事项等信号，并分析其对报告可信度和后续核查范围的影响。

审计意见并不自动等于某一具体风险事实。系统会把意见类型作为独立证据，再检查是否存在对应的存货、应收、收入确认、持续经营或披露风险条目，避免只在正文提到而不进入风险台账。

### 7.3 法规和监管检索

法规检索需要核对：

- 适用期间。
- 法规版本。
- 事项范围和适用条件。
- 被检索文本是否为正式来源。
- 企业事实是否真的满足条款条件。

没有外部监管数据库或没有匹配记录时，只能表述“在实际检索范围内未发现”，不能表述“企业不存在处罚”或“已经完全合规”。

### 7.4 行业与经营风险

行业展望模块通过 `industry_outlook` 获取行业事件、景气度和风险传导线索，必要时由法规和监管问询工具补充政策背景。行业信息用于解释经营环境和风险传导，不直接替代公司年报证据，也不生成买入或卖出建议。

## 8. 量化模型与综合评分

### 8.1 Z-Score 与 M-Score 的定位

系统支持 Altman Z-Score 和 Beneish M-Score，但两者仅作为风险筛查和交叉印证：

- 计算前检查必要输入、单位、期间和适用性。
- 输入不足时保留 `insufficient_data` 或 `not_applicable` 状态。
- 半年度或季度报告可以输出近似分值，但必须同时展示 `interim_note` 或 `limitation`。
- 模型信号不能单独决定风险等级。
- 模型信号不能直接证明破产、造假、违法或错报。

### 8.2 综合评分

综合评分由可用工具维度汇总，主要关注财务、披露和校验等维度。系统区分：

- `score_status`：当前评分是否具备进入统计的来源条件。
- `score_note`：评分的适用性和限制。
- `level_floor_adjustment`：审计意见、持续经营等信号触发的等级底线。

候选风险数量不参与评分，正式风险数量也不等同于评分。评分缺少有效输入时显示限制，不使用中性分数掩盖缺失。

### 8.3 风险等级与人工复核

等级是建议关注优先级，不是审计意见。正式报告同时展示证据状态、验证状态、置信度和建议核查程序。未通过证据门禁的候选项只能进入待复核层，不能通过改写文字直接升级为正式风险。

## 9. 结构化结果、证据链与风险门禁

### 9.1 四类核心记录

`src/core/result_contract.py` 定义了跨工具和跨产物共享的核心契约：

| 对象 | 关键字段 | 业务作用 |
| --- | --- | --- |
| `Fact` | 字段、原始值、规范值、单位、期间、页码、定位、摘录 | 证明原始材料中到底出现了什么 |
| `Evidence` | 来源类型、摘录、事实编号、指标编号、核验状态 | 把事实或指标连接到风险条目 |
| `MetricResult` | 名称、公式、输入、代入过程、数值、状态、限制、证据编号 | 让人工可以复算指标 |
| `RiskFinding` | 风险 ID、维度、标题、等级、证据、置信度、验证状态、复核建议 | 承载可审阅的风险对象 |
| `ArtifactManifest` | 类型、路径、状态、哈希、版本、快照 ID | 证明产物是否成功生成并对应哪一批分析 |

### 9.2 证据链结构

```text
源文件 / 页码 / 原文摘录
        ↓
Fact：规范化事实
        ↓
MetricResult：公式、代入、数值和状态
        ↓
Evidence：核验后的证据连接
        ↓
RiskFinding：风险描述、等级、置信度和程序建议
        ↓
report_snapshot：最终发布快照
```

每条正式风险必须能够回指至少一条可用证据。证据需要满足：

- 证据编号存在于证据目录。
- 证据有原文摘录。
- 证据能够回指事实、指标或来源位置。
- 证据来源状态已核验。
- 风险与证据之间的维度和语义关系合理。

### 9.3 来源状态

系统使用跨页面和产物统一的来源状态：

| 状态 | 中文含义 | 评分资格 |
| --- | --- | --- |
| `verified` | 已核验 | 可以进入评分和正式风险门禁 |
| `incomplete` | 数据源不完整，仅供参考 | 默认不进入正式评分 |
| `unverified` | 来源未核验，仅供人工复核 | 不进入正式评分 |
| `demo_placeholder` | 演示占位数据，不代表公司实际数据 | 不进入正式结论 |

### 9.4 C2 双隔离语义复核

C2 只复核会影响正式风险成立与否的关键语义，不重复检查确定性计算。系统使用两次相互隔离的判断：

1. 判断风险事实、事项性质和规则条件是否被证据支持。
2. 在隔离上下文中独立复核同一风险。

两次判断必须在关键条件和证据引用上对齐，才允许风险进入正式采信层。输出非法、缺少证据或两次判断不一致时，风险降为待复核。

### 9.5 C1 关注方、否定方与仲裁

C1 负责处理复杂候选风险：

```text
关注方：提出风险成立理由并引用证据
   ↓
否定方：寻找替代解释、口径问题和证据缺口
   ↓
仲裁方：比较双方证据，给出最终状态和必要调整
   ↓
重新绑定证据、重新分层、重新同步发布快照
```

关注方不能单方面升级风险，否定方也不能因为没有完整材料就证明“没有风险”。仲裁结果只允许写入白名单状态和等级，新增风险必须带维度、证据和置信度。

### 9.6 风险门禁的核心逻辑

`src/agents/agent.py::_apply_review_gates` 对每条风险执行以下判断：

```python
# src/agents/agent.py::_apply_review_gates 的核心判断
evidence_ok = (
    bool(evidence_ids)
    and bool(str(risk.get("evidence", "") or "").strip())
    and all(
        str(evidence_id) in evidence_catalog
        and usable_evidence(evidence_catalog[str(evidence_id)])
        for evidence_id in evidence_ids
    )
)

c2_evidence_ok = bool(c2_evidence_ids) and all(
    evidence_id in evidence_catalog
    and usable_evidence(evidence_catalog[evidence_id])
    for evidence_id in c2_evidence_ids
)

if not evidence_ok or risk.get("evidence_pending") \
        or risk.get("pending_verification"):
    risk["formal_status"] = "unaccepted"
    risk["status"] = "pending_evidence"
elif review_enabled and c2_result.get("status") == "completed":
    supported = bool(
        c2 and c2.get("decision_1") == "supported"
        and c2.get("decision_2") == "supported"
    )
    if c2 and c2.get("state") == "consistent" \
            and c2_evidence_ok and supported:
        risk["formal_status"] = "accepted"
    else:
        risk["formal_status"] = "unaccepted"
        risk["status"] = "pending_review"
```

上述摘录对应实际门禁分支。完整实现还会处理历史字段兼容、证据编号回填、风险数量同步、等级底线、审查预算和评分状态；任何未通过证据或语义门禁的条目都会进入 `pending_items`，不能计入正式风险总数。

### 10.1 单一事实源

`src/core/report_snapshot.py` 负责把工具结果、模型结果和复核结果归一化为 `report_snapshot`。快照通常包含：

```text
snapshot_id
analysis_id
company_info
facts
metrics
evidence
risks.formal
risks.pending
risks.excluded
validation
disclosure
risk_models
score
review_gate
artifact_manifest
rendering
```

`snapshot_id` 根据规范化快照内容生成。产物清单回写路径和文件哈希时，不改变快照的业务身份。Web、PDF、Excel、TXT、JSON、历史记录和 manifest 都从快照或其集中适配器读取，不在各自渲染层重新猜测风险数量和评分。

### 10.2 公共展示与内部字段

内部历史字段继续保留，是为了兼容旧数据、评分和门禁；公共输出必须使用明确、可理解且不直接作结论的中文表述。

公共展示口径如下：

| 产物 | 公共展示规则 |
| --- | --- |
| Web | 展示正式风险、风险依据、数量和“待复核提示”数量及简短提醒 |
| PDF | 展示正式风险和轻量“待复核提示”，不把机器复核 JSON 直接塞进正文 |
| Excel | 保留完整“待复核事项”明细、依据、来源、页码和核查建议 |
| TXT/JSON | 保留完整结构化台账，适合机器读取和后续复核 |

PDF 和 Web 不展示内部控制字段名、机器复核 JSON 键或历史兼容标签。报告正文中的风险维度统一使用“财务风险”“数据勾稽与可靠性”“信息披露与合规”“持续经营与偿债”“监管问询与处罚”等公共名称。

### 10.3 公共文本净化

`src/tools/pdf_export.py` 使用 JSON 解析器识别嵌套结构，而不是用正则简单截断。净化流程包括：

- 递归识别复核对象、数组和嵌套字段。
- 移除机器复核对象，保留可阅读的复核摘要。
- 将内部字段名映射为中文标题，无法对外解释的控制字段直接过滤。
- 保留可执行的人工核查程序。
- 过滤确定性结论化的内部标签，统一替换为公共风险名称。

这一步解决了长 JSON 进入报告卡片造成溢出、英文键泄漏和 PDF 出现机器辩论正文的问题。

### 10.4 PDF、Excel 与 Web 的信息密度差异

三类产物不追求完全相同的版式，而追求同一事实源下的合理信息密度：

- PDF 面向管理层和专业人员阅读，展示摘要、风险明细、图表和轻量待复核提示。
- Excel 面向审计底稿和人工复核，保留完整来源、输入、公式、证据和待复核事项。
- Web 面向交互演示，展示阶段进度、结构化结果、折叠台账和产物链接。

PDF 的长风险内容允许在段落边界自然分页，标题尽量和首条风险内容同页，避免孤立章节标题和大面积空白。

### 12.2 评估接口的实现边界

`/api/evaluate/run?mode=tool` 保持原地址和返回结构，默认执行本地确定性工具评估。接口与命令行共用 `tests/evaluation_report.py`，同步评估放进 `asyncio.to_thread`，避免阻塞 FastAPI 事件循环，并统一项目根目录、输入路径和结果输出路径。

核心实现如下：

```python
# src/main.py::run_evaluation
project_root = Path(__file__).resolve().parents[1]
script_path = project_root / "tests" / "evaluation_report.py"

def _run_tool():
    spec = importlib.util.spec_from_file_location(
        "evaluation_report_service", script_path
    )
    module = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(module)
    output_path = project_root / "tests" / "evaluation_results.json"
    return module.run_evaluation("tool", str(output_path))

data = await asyncio.wait_for(
    asyncio.to_thread(_run_tool),
    timeout=30,
)
return {"status": "ok", "mode": "tool", "data": data}
```

接口层只负责调度和错误返回，评估规则仍由统一服务函数负责。Agent 全链路评估耗时较长，保留命令行入口，不在普通 Web 请求中假装是快速接口。

## 14. 安全、可靠性与故障降级

### 14.1 上传与路径安全

上传接口执行扩展名白名单、文件大小限制、分块写入、SHA-256、文件名清洗和工作目录约束。远程 PDF 地址需要经过主机解析和 IP 检查，拒绝回环、私有、链路本地、保留和未指定地址，重定向逐跳重新校验。

这些措施解决的是输入边界和访问安全，不代表文件内容本身已经正确，也不替代财务事实核验。

### 14.2 工具失败和阶段失败

工具输出不是合法 JSON 时，阶段交接会登记 `invalid_tool_result`，不会把失败当成“没有风险”。某个阶段没有有效摘要时，下一阶段会收到显式失败说明，并将相关事项标记为单方发现或待复核。

导出失败时，manifest 记录 `partial` 或 `failed`，而不是把缺失文件显示成成功。历史、当前批次和旧产物按批次隔离。

### 14.3 长文本和上下文控制

系统对原始文本设置上限，对消息使用滑窗，对工具结果使用不丢失结构化状态的投影摘要，同时维护不受滑窗裁剪的工具台账。这样既控制模型上下文，也避免早期财务校验结果在综合阶段消失。

## 15. 限制、边界与不应夸大的结论

当前系统仍有以下边界：

1. 扫描型 PDF、图片表格和复杂版式可能需要 OCR 或人工补录。
2. 文本筛查不能证明法律意义上的完整披露或不存在违法事实。
3. 行业基准只有在来源、行业、期间和计算定义可比时才有解释价值。
4. 中期报告的年度模型阈值存在适用性限制，只能作为交叉印证。
5. 监管检索受到公开数据库、网络可用性和检索范围限制。
6. 量化分数不是审计结论，正式风险仍需要人工复核原始凭证、合同、函证和附注。
7. 缺失证据会降低风险采信资格，不应被解释为企业没有风险。
8. 评估样例不能代表所有行业、所有会计准则和所有年报版式。

因此系统对外统一使用“风险线索”“审计核查关注”“待复核提示”“在实际检索范围内未发现”等措辞，避免把智能体输出包装成监管或审计机关的确定性认定。

## 附录 B：技术边界说明

### B.1 模型与规则的职责边界

规则和 Python 工具擅长抽取、计算和校验，但年报中的风险解释、跨章节关联、法规语义匹配和审计核查建议需要理解自然语言。系统让大模型负责任务组织和解释，同时把事实、计算和采信边界留在确定性代码中。

### B.2 终局发布不由大模型直接完成

因为最终 PDF 必须包含复核回写后的风险、统一数量和最终产物身份。导出由快照和系统后处理完成，可以避免模型在上下文不完整时生成与 Web、Excel 不一致的报告。

### B.3 缺失数据处理边界

不填零、不填中性值、不用模型猜测。全部缺失时不生成空条目，部分缺失时保留指标并标明缺失字段，缺失会影响评分资格和风险层级。

### B.4 行业基准的适用边界

不是。行业基准只是在来源、行业、期间和定义可比时提供筛查参照，不能单独作为风险定级或合规判断依据。

### B.5 系统输出与审计意见的边界

不是。系统输出风险线索、证据链和核查程序建议，最终审计判断仍需要具备资质的专业人员结合原始凭证、合同、函证、现场程序和适用准则完成。

## 附录 C：报告结语

本项目的技术核心可以归纳为一条可复现的链路：

```text
智能体拆解任务
  + 确定性工具计算事实
  + 结构化契约保存证据
  + C2/C1 复核处理语义不确定性
  + 证据门禁区分正式风险与待复核事项
  + 终局快照统一所有产物
  = 面向年报分析业务的可演示、可解释、可复核智能体系统
```

这条链路是本系统相对于单纯文本问答的主要差异，也是判断系统业务有效性时的核心依据。
